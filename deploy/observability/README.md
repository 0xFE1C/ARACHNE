# Observability as code

This directory holds the artefacts that turn ARACHNE's metrics into decisions an operator
can be held to. All of them are versioned here, reviewed like code, and checked in CI.

| Path | What it is | Regenerated by |
|---|---|---|
| `slos/*.yaml` | The service-level objectives: target, window, measurement query, runbook | hand-written |
| `alerts/arachne-slo-burn.yaml` | Prometheus recording rules and error-budget burn alerts | `python -m arachne.ops.slo --render` |
| `dashboards/arachne-slo.json` | A Grafana dashboard with one panel pair per objective | `python -m arachne.ops.slo --render` |

## The objectives

| Objective | Indicator | Target | Window |
|---|---|---|---|
| `api-availability` | requests answered outside 5xx ÷ all requests | 99.9 % | 30 d |
| `api-latency` | requests answered within 500 ms ÷ all requests | 99 % | 30 d |
| `scan-completion` | scans completed ÷ finished scans | 95 % | 7 d |

Each definition names the metric and the labels it measures, and
`tests/unit/test_slo_contract.py` resolves every one of them against
`arachne.core.metrics.METRIC_FAMILIES` — the declaration `GET /metrics` renders from. A
definition that named a metric (or a label, or a histogram bucket) the endpoint does not
expose fails that test rather than producing an empty panel.

## Loading the artefacts

The alert rules are a plain Prometheus rule file, so loading them is copying them where your
Prometheus (or a compatible rule loader) reads them:

```bash
# Kubernetes: a ConfigMap the Prometheus rule selector matches.
kubectl create configmap arachne-slo-rules \
    --from-file=arachne-slo-burn.yaml=deploy/observability/alerts/arachne-slo-burn.yaml

# Or a bare Prometheus.
cp deploy/observability/alerts/arachne-slo-burn.yaml /etc/prometheus/rules/
promtool check rules /etc/prometheus/rules/arachne-slo-burn.yaml
```

The rules only *read* the metrics ARACHNE already publishes; they need no exporter of their
own. Two dependencies are worth stating plainly:

* **A scrape target.** Prometheus must be pointed at `GET /metrics` on the API (and on each
  agent worker, if the scan-farm objective is to cover the whole fleet — `arachne_scans_total`
  is a per-process counter).
* **Recording-rule evaluation.** The alerts compare against the generated
  `arachne:slo_<id>:burn_rate_<window>` series, so the `arachne-slo-burn` group must be
  evaluated by the same server that evaluates the alerts. That is one group, and it is
  self-contained.

## Loading the dashboard

`dashboards/arachne-slo.json` is a Grafana dashboard with two panels per objective: the
indicator itself (a `stat` panel with the target as its green threshold) and the burn rate over
both alert windows. It is generated from the same definitions as the alerts, so the query on a
panel *is* the measurement query the objective is scored by.

```bash
# Grafana provisioning: point a dashboard provider at the file, or import it in the UI.
curl -sS -X POST "$GRAFANA/api/dashboards/db" \
  -H "Authorization: Bearer $GRAFANA_TOKEN" -H 'Content-Type: application/json' \
  --data-binary @<(python - <<'PY'
import json, pathlib
model = json.loads(pathlib.Path("deploy/observability/dashboards/arachne-slo.json").read_text())
print(json.dumps({"dashboard": model, "overwrite": True, "message": "arachne SLOs"}))
PY
)
```

The dashboard has a `datasource` template variable, so it binds to whichever Prometheus
datasource the deployment uses rather than to a name baked in here.

## Changing an objective

1. Edit the definition in `slos/`.
2. Regenerate the alerts: `python -m arachne.ops.slo --render`.
3. Run the gate: `python -m arachne.ops.slo --check` (or `arachne slo check`). This fails if a
   definition names a metric the endpoint does not expose, if the objective window is not the
   window the query measures, or if the committed alert rules are not what the definitions
   generate.
4. Read the runbook section the definition points at, and update it if the response changed:
   `docs/operator-guide.md` §52.
